## Interpretation so far
- Trees fire on ~64% of eligible rounds at 0.45/2 and spend ~21% more verifier rows per output token but only gain ~4% more accepted drafts/token; per-candidate efficiency stays far below linear (~58% vs ~91% conditional). Net end-to-end is neutral-to-slightly-negative, inside noise but no measured win.
- The narrow window (T<=8 rows, same cost whether linear or tree) means a tree round must beat the linear round's accepted-row yield (~4.5+/round implied by control's 4,491 accepts) or it loses verify bandwidth. Linear rounds accept heavily at 0.7 draft_conf, so low-P sibling rows are usually wasted bandwidth.
- Question for the audit: how to raise accepted drafts per tree round above the linear counterfactual, e.g. (a) branch only where the linear round's expected continuation yield is low (uncertainty-aware cut/shape choice, expected-value model of P(accept-depth) per node), (b) better sibling choice than top runner-up conditional (dedup vs prefix, position-conditional calibration), (c) depth-vs-fanout budget allocation (deep chain vs wide at cut), (d) shape selection from recent acceptance telemetry (adaptive policy à la Df2AdaptiveSolo), (e) tree-aware accept: use rejected-sibling signal for next-round drafting. Telemetry exists: `[accept-hist]` per-request histograms (df2_pos_reached/accept, tree_node_reached/accept by depth, tree_rounds, tree_branch_hits).
- Correctness policy (owner decision, 2026-11-24): candidate-1 baseline. Accepted branch changes continuation state; no bitwise parity requirement vs linear; validate via deterministic acceptance telemetry + deterministic quality scores, not full-output equality.
